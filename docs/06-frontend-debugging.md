# 🔍 06. Frontend Debugging Guide (React & Modern Web)

คู่มือและแนวทางปฏิบัติในการตรวจสอบหาจุดบกพร่อง (Debugging) ฝั่ง Frontend เพื่อช่วยให้ค้นพบและแก้ไขปัญหาระบบได้อย่างรวดเร็ว แม่นยำ และเป็นมืออาชีพ

---

## 🍪 1. การดักเช็กระบบ Auth & Cookies (สำคัญที่สุดเมื่อใช้ร่วมกับ Render Backend)

เมื่อระบบหลังบ้านส่งคุกกี้แบบ `HttpOnly` มา หน้าบ้านจะไม่สามารถใช้คำสั่ง JavaScript ตรวจดูได้ วิธีการตรวจสอบที่ถูกต้องคือการใช้ **Browser DevTools**

### 🌐 วิธีตรวจว่าคุกกี้เข้าเครื่องจริงไหม
1. เปิดหน้าเว็บ ➡️ กดปุ่ม `F12` บนคีย์บอร์ดเพื่อเปิด Browser DevTools
2. ไปที่แท็บ **Application** (สำหรับ Chrome/Edge) หรือ **Storage** (สำหรับ Firefox)
3. เมนูด้านซ้ายใต้หัวข้อ **Storage** ➡️ ให้คลิกขยายที่คำว่า **Cookies** ➡️ เลือก URL เว็บของคุณ
4. **สิ่งที่คุณต้องเห็น:** 
   * ต้องมีคุกกี้ชื่อ `accessToken` ปรากฏขึ้นมาในตาราง
   * คอลัมน์ **HttpOnly** และ **Secure** ต้องขึ้นเครื่องหมายติ๊กถูก (เป็นสีเขียว/น้ำเงิน) เมื่อรันบนระบบจริง (Render)
   * คอลัมน์ **SameSite** ต้องขึ้นคำว่า `None` บนระบบจริง และขึ้น `Lax` ตอนรันบนเครื่องตัวเอง

### 🚨 บั๊กรอดตาย: ยิง API แล้วคุกกี้ไม่ยอมแนบกลับไปหลังบ้าน?
* **สาเหตุ:** ลืมเปิดใช้งานสิทธิ์รับส่งคุกกี้ข้ามโดเมน
* **วิธีเช็ก:** ไปที่แท็บ **Network** ➡️ คลิกที่ชื่อ Request API ที่ยิงไม่ผ่าน ➡️ ดูที่แถบ **Headers** ข้อมูลในส่วน **Request Cookies** จะต้องว่างเปล่า
* **วิธีแก้ไข:** ตรวจสอบให้มั่นใจว่าไฟล์ `apiClient.js` ส่วนกลาง มีการสั่งเปิด `withCredentials: true` แล้วเรียบร้อย

## 📡 2. การแกะรอยเน็ตเวิร์ก (Network Traffic Inspection)

แท็บ **Network** ใน DevTools คือด่านแรกที่ต้องใช้ดูว่าหน้าบ้านส่งข้อมูลไปถูกกล่อง และหลังบ้านตอบกลับมาถูกเรื่องหรือไม่

### 🔍 ขั้นตอนการไล่เช็ก Request
1. เปิดแท็บ **Network** ➡️ เลือกตัวกรองประเภทไฟล์เป็น **Fetch/XHR** เพื่อดูเฉพาะการยิง API
2. ดูที่คอลัมน์ **Status (รหัสสถานะ)**:
   * `200` หรือ `201`: ยิงผ่าน ข้อมูลไปถึงและกลับมาสำเร็จ
   * `400 Bad Request`: หน้าบ้านส่งข้อมูล (Payload) ไปผิดฟอร์แมต หรือลืมส่งฟิลด์ที่หลังบ้านต้องการ
   * `401 Unauthorized`: คุกกี้หมดอายุ หรือลืมใส่ `withCredentials`
   * `403 Forbidden`: สิทธิ์ไม่ถึง (เช่น สมาชิกทั่วไปแอบยิงเข้า API ของ Admin)
   * `500 Internal Server Error`: หลังบ้านระเบิด/ล่ม ให้ไปไล่ดู Error Logs บน Dashboard ของ Render
3. คลิกดูแท็บ **Payload** ➡️ ตรวจสอบว่า `email` หรือ `password` ส่งไปในรูปแบบ JSON ที่ถูกต้องหรือไม่
4. คลิกดูแท็บ **Response** ➡️ ดูว่าโครงสร้างข้อมูลที่ส่งกลับมา ตรงกับที่ฟังก์ชันหน้าบ้านกำลังแกะไปใช้งานหรือไม่

## ⚛️ 3. การตรวจสอบสเตตัสด้วย React DevTools Extension

การใช้ `console.log` ปริ้นต์ค่าวางทิ้งไว้ทั่วแอปจะทำให้โค้ดรกและไล่เช็กยาก แนะนำให้ติดตั้ง Extension ที่ชื่อว่า **React Developer Tools** บนเบราว์เซอร์

### 🛠️ เครื่องมือหลัก 2 ตัวที่ต้องใช้:

#### 1. แท็บ ⚛️ Components (ใช้ดูโครงสร้างและสเตตัส)
* ค้นหาคอมโพเนนต์ที่คุณต้องการตรวจสอบในโครงสร้างต้นไม้ (Component Tree)
* เมนูด้านขวาจะแสดงค่า **Props**, **State** และ **Hooks** ที่คอมโพเนนต์นั้นกำลังถืออยู่ ณ วินาทีนั้นแบบ Real-time
* **เคสตัวอย่าง:** ถ้าอยากรู้ว่า `AuthContext` ทำงานได้จริงไหม ให้คลิกที่ `<AuthProvider>` แล้วดูที่หัวข้อ `value` ว่ามีข้อมูลของผู้ใช้หลุดเข้ามาหลังจากล็อกอินสำเร็จแล้วหรือยัง

#### 2. แท็บ ⚛️ Profiler (ใช้หาจุดที่ทำให้เว็บกระตุก/ช้า)
* ใช้สำหรับบันทึก (Record) พฤติกรรมการทำงานของหน้าเว็บ
* ช่วยให้ค้นพบว่ามีคอมโพเนนต์ไหนที่เกิดการ **Re-render พร่ำเพรื่อ (Wasteful Re-renders)** เกินความจำเป็น เพื่อที่คุณจะได้นำ `useMemo` หรือ `useCallback` ไปครอบดักปัญหาได้ตรงจุด

## 🛠️ 4. เทคนิคระดับโปร: หยุดเวลาโค้ดด้วย `debugger` และ Breakpoints

แทนที่จะพิมพ์ `console.log(data)` สลับไปสลับมา ให้เปลี่ยนมาใช้การหยุดเวลาของ JavaScript เพื่อตรวจสอบสแนปชอตของข้อมูล ณ วินาทีนั้นได้ทันที

### วิธีที่ 1: พิมพ์คำสั่งฝังในโค้ดตรง ๆ
เมื่อเปิดหน้าเว็บทิ้งไว้และเปิด DevTools ค้างอยู่ ทันทีที่ระบบวิ่งมาเจอคำสั่งนี้ หน้าจอเบราว์เซอร์จะหยุดนิ่งชั่วคราว (Freeze) ให้คุณเอาเมาส์ชี้ดูค่าตัวแปรในโค้ดตอนนั้นได้เลย

```javascript
const handleSubmit = async (e) => {
    e.preventDefault();
    const result = await login(email, password);
    
    debugger; // ⬅️ โค้ดจะหยุดกึ๊กตรงนี้ เพื่อให้เราเช็กค่าตัวแปร 'result' ใน DevTools ได้แบบสด ๆ
    
    if (result.success) {
        navigate('/dashboard');
    }
};
```

### วิธีที่ 2: วาง Breakpoints บน DevTools (ไม่ต้องแก้โค้ด)
1. ไปที่แท็บ **Sources** (หรือ **Debugger** ใน Firefox)
2. กดปุ่ม `Ctrl + P` (หรือ `Cmd + P` บน Mac) ➡️ พิมพ์ค้นหาชื่อไฟล์ที่ต้องการตรวจสอบ เช่น `AuthContext.jsx`
3. คลิกเลือก **เลขบรรทัด** ที่คุณต้องการให้โค้ดหยุดทำงาน
4. เมื่อคุณกดคลิกปุ่มบนหน้าเว็บแล้วโค้ดทำงานมาถึงบรรทัดนั้น ระบบจะหยุดเวลาให้คุณตรวจสอบข้อมูล และสามารถกดปุ่มลูกศรเพื่อสั่งให้โค้ดเดินหน้าทีละสเต็ป (Step Over) เพื่อดูทิศทางการไหลของข้อมูลได้

## 🚨 5. รายการบั๊กยอดฮิตฝั่ง Frontend และวิธีจัดการ (Troubleshooting Cheat Sheet)


| อาการของปัญหา | สาเหตุที่เป็นไปได้ | แนวทางการแก้ไขที่ตรงจุด |
| :--- | :--- | :--- |
| **หน้าเว็บขาวโพลน (White Screen of Death)** | 1. เกิด Runtime Error รุนแรงภายในโค้ดจนแอปพลิเคชันพังทลาย<br>2. การ Import พังหลังจากย้าย Folder (Module Not Found) | 1. ติดตั้ง `Error Boundary` (ตามคู่มือ Best Practice) ครอบไว้ชั้นบนสุด<br>2. ตรวจสอบ `vite.config.js` ว่ามี `@` alias หรือยัง และเปลี่ยนการ Import เป็น `@/` |
| **Error: useAuth must be used within...** | เรียกใช้ `useAuth` จาก Path ที่ผิด หรือลืมครอบ `AppProvider` ที่ `main.jsx` | ตรวจสอบให้มั่นใจว่า Import `useAuth` มาจาก `@/shared/contexts/AuthContext` เท่านั้น |
| **ค้างอยู่ที่หน้าโหลดตลอดเวลา (Infinite Loading)** | ลืมใส่บล็อก `finally` เพื่อปิดสเตตัส loading หรือยิง API แล้ว error หลุดรอดไปโดยไม่มี catch ดักไว้ | ตรวจสอบว่าใน `try-catch` ฝั่งยิง API มีการสั่ง `setLoading(false)` ภายในบล็อก `finally` เสมอ |
| **ข้อมูลในหน้าจอไม่ยอมอัปเดตตามค่าใหม่** | เกิดปัญหาการส่ง Props ลึกเกินไป หรือลืมพึ่งพาตัวแปรในกล่อง Dependency Array ของ `useEffect` | ย้ายสถานะนั้นไปจัดการผ่าน Context หรือ Custom Hook และตรวจสอบคีย์ของอาร์เรย์ท้าย `useEffect` ให้ครบถ้วน |
| **TypeError: Cannot read properties of null** | พยายามดึงฟิลด์ข้อมูลจากอาร์เรย์หรือออบเจกต์ที่ยังโหลดมาไม่เสร็จ (เป็น `null` หรือ `undefined`) | ใช้ระบบเซฟตี้คัตด้วยคำสั่ง **Optional Chaining (`?.`)** เช่น เปลี่ยนจาก `user.name` เป็น `user?.name` เพื่อให้ระบบข้ามไปทำงานต่อได้โดยไม่ล่ม |
