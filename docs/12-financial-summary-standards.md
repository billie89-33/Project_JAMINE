# 📊 12. Financial Summary Standards (Shared UI, Isolated Logic)

เอกสารนี้รวบรวมมาตรฐานการออกแบบและพัฒนส่วนสรุปยอดเงิน (Cart Summary / Order Summary) ซึ่งเป็นส่วนที่สำคัญที่สุดในระบบ E-commerce เพื่อสร้างความเชื่อมั่นให้กับลูกค้าและป้องกันความผิดพลาดทางเงิน

---

## 🏛️ 1. รูปแบบ "แชร์หน้าตา แยกสมอง" (Shared UI, Isolated Logic)
**หลักการ:** ใช้คอมโพเนนต์แสดงผลตัวเดียวกัน (`OrderSummaryCard.jsx`) ตลอดทั้ง Order Flow แต่ใช้แหล่งข้อมูลและ Logic การทำงานที่แยกออกจากกันตามบริบทของหน้านั้นๆ

### ✅ ทำไมต้องใช้รูปแบบนี้?
1. **Visual Trust:** ลูกค้าจะรู้สึกปลอดภัยเมื่อเห็นยอดเงินและรูปแบบการสรุปที่คุ้นเคยตั้งแต่วันหน้าตะกร้าจนถึงหน้าชำระเงิน
2. **Maintainability:** หากต้องเปลี่ยนดีไซน์ (เช่น เปลี่ยนฟอนต์ราคาทั้งเว็บ) แก้ที่จุดเดียวจะเปลี่ยนให้ทั้งแอป
3. **Data Integrity:** ป้องกันบั๊กราคาไม่ตรงระหว่างหน้า เพราะแต่ละหน้าจะรับผิดชอบการดึงข้อมูลจาก API ที่ถูกต้องของตัวเอง

---

## 🛡️ 2. มาตรฐานความปลอดภัยและสิ่งที่ต้องระวัง (Security & Precautions)

เพื่อให้ระบบมีความปลอดภัยระดับ Enterprise ทุกส่วนที่เกี่ยวข้องกับตัวเลขต้องปฏิบัติตามกฎดังนี้:

### 🚫 2.1 ห้ามคำนวณเงินที่หน้าบ้าน (No Client-side Calculation)
*   **กฎ:** ห้ามใช้ `.reduce()` หรือการบวกเลขเพื่อหายอด `Total` ที่ฝั่ง Frontend เด็ดขาด
*   **เหตุผล:** ป้องกันความคลาดเคลื่อนของตัวเลข และป้องกันผู้ใช้ที่มีความรู้ด้านเทคนิคแก้ไข Logic ผ่าน Browser Console
*   **แนวทาง:** ให้แสดงผลยอด `subtotal`, `shipping`, `discount`, และ `total` จาก API Response เท่านั้น (**Trust the Backend**)

### 🛡️ 2.2 การป้องกันการปลอมแปลงยอดเงิน (Tampering Prevention)
*   **กฎ:** ในขั้นตอนการสร้างคำสั่งซื้อ (Submit Order) **ห้ามส่งยอดเงินรวม (totalAmount)** กลับไปให้ Backend
*   **ห้ามรับราคาสินค้าจาก Frontend:** หลังบ้านต้องใช้ราคาจาก Database ของตัวเองเท่านั้น ห้ามใช้ราคาที่ส่งมาจาก Client (Never Trust Frontend Prices)
*   **แนวทาง:** ส่งเฉพาะข้อมูลที่จำเป็น เช่น `addressId` และ `paymentMethod` เท่านั้น ส่วนยอดเงินและรายการสินค้า Backend ต้องดึงจาก Database/Cart ของผู้ใช้มาคำนวณเองที่ฝั่ง Server

---

## 📸 3. มาตรฐาน Order Snapshot (หัวใจของความถูกต้อง)
**หลักการ:** ห้ามอ้างอิง (Reference) ข้อมูลที่เปลี่ยนแปลงได้ในอนาคตลงในออเดอร์ ต้องทำการ **Snapshot** ข้อมูล ณ วินาทีที่กดซื้อเสมอ:

1.  **Price Snapshot:** บันทึกราคา (`priceAtPurchase`) ณ วินาทีที่ซื้อ ป้องกันราคาสินค้าเปลี่ยนในภายหลังแล้วออเดอร์เพี้ยน
2.  **Address Snapshot:** บันทึกที่อยู่จัดส่งแบบละเอียด (String) ไม่ใช่แค่ ID เพื่อใช้เป็นหลักฐานทางกฎหมายและการจัดส่ง
3.  **Product Info Snapshot:** บันทึกชื่อรุ่น (`modelName`) และรูปภาพหลักไว้ในออเดอร์ ป้องกันกรณีสินค้าถูกลบออกจากร้าน

---

## ⚙️ 4. Order State Machine (การควบคุมสถานะ)
สถานะออเดอร์ต้องไหลไปตามทิศทางที่กำหนดเท่านั้น (Valid Transitions):
*   `pending` ➔ `paid` (สำเร็จ)
*   `pending` ➔ `cancelled` (ล้มเหลว/หมดอายุ)
*   **ข้อห้าม:** ห้ามเปลี่ยนจาก `cancelled` กลับมาเป็น `paid` เด็ดขาด เพื่อป้องกันการรับเงินจากออเดอร์ที่คืนสต็อกไปแล้ว

---

## 🛠️ 5. มาตรฐานการรับ-ส่งข้อมูล (Data Handling)

คอมโพเนนต์ `OrderSummaryCard` ควรรับ Props พื้นฐาน 4 อย่างเสมอ:
1. `subtotal`: ราคารวมสินค้า (ก่อนค่าส่ง/ส่วนลด)
2. `shipping`: ค่าจัดส่ง (แสดง "Free" หากเป็น 0)
3. `discount`: ส่วนลด (ถ้ามี)
4. `total`: ยอดสุทธิที่ต้องจ่ายจริง

---

## ⚠️ 4. จุดที่ต้องตรวจสอบเป็นพิเศษ (Final Checklist)

| จุดที่ต้องระวัง | คำแนะนำ |
| :--- | :--- |
| **Race Conditions** | ระหว่างที่ API กำลังคำนวณยอดใหม่ (เช่น หลังเปลี่ยนที่อยู่) ต้องมี Loading Overlay และปิดปุ่มดำเนินการชั่วคราว |
| **Step Integrity** | ตรวจสอบว่าผู้ใช้ไม่สามารถข้ามหน้า (เช่น พิมพ์ URL ไปหน้า Payment ตรงๆ) โดยไม่มีข้อมูล Order ที่ถูกต้องจาก Backend |
| **Formatting** | ใช้ `.toLocaleString()` ในการแสดงผลตัวเลขเสมอเพื่อความเป็นสากลและอ่านง่าย |
