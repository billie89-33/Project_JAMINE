# 🧠 16. Dynamic Architecture & Refactoring Lessons

บทสรุป "มหากาพย์การ Refactor ระบบสินค้า" เพื่อยกระดับจากระบบ Hardcode ไปสู่ **Dynamic Enterprise Architecture 100%** เอกสารนี้รวบรวมสิ่งที่ควรหลีกเลี่ยง (Anti-Patterns) และสิ่งที่ควรปฏิบัติ (Best Practices) เพื่อเป็นบทเรียนสำหรับฟีเจอร์อื่นๆ ในอนาคต

---

## 🚫 สิ่งที่ "ไม่ควรทำ" (Anti-Patterns & Technical Debts)

จากการตรวจสอบระบบเดิม เราพบจุดอ่อนที่ทำให้ระบบไม่สามารถขยายตัว (Scale) ได้:

1.  **Hardcode Component Routing (สถาปัตยกรรมแบบ Fix หน้า):**
    *   **ปัญหา:** การใช้ `ProductSwitchCase` เพื่อแยกเรนเดอร์คอมโพเนนต์ตามหมวดหมู่ (เช่น `<NotebookSpecs />`, `<RAMSpecs />`)
    *   **ผลกระทบ:** เมื่อ Backend เพิ่มหมวดหมู่ใหม่ เช่น "Speaker" หน้าเว็บจะพังทันทีเพราะไม่มี Case รองรับ ทำให้โปรแกรมเมอร์ต้องมาเขียนโค้ดเพิ่มทุกครั้งที่มีสินค้าประเภทใหม่
2.  **Hardcode Data Templates (การฟิกซ์โครงสร้างข้อมูล):**
    *   **ปัญหา:** การสร้าง Object ตายตัวเพื่อคุมแบบฟอร์ม เช่น `CATEGORY_TEMPLATES` ที่บังคับว่า Keyboard ต้องมี 15 ฟิลด์เป๊ะๆ
    *   **ผลกระทบ:** ฐานข้อมูลจะเต็มไปด้วย "ค่าว่าง (Empty fields)" สำหรับสินค้าที่สเปคไม่ครบ และไม่รองรับฟีเจอร์ใหม่ๆ ที่เพิ่มเข้ามาในสินค้ารุ่นพิเศษ
3.  **Infinite Render Loops ใน Custom Hooks:**
    *   **ปัญหา:** การส่ง Object เป็นพารามิเตอร์เข้าไปใน Hook แบบ Inline (เช่น `useApi(api, { onSuccess: () => {} })`) โดยไม่จัดการ Reference ให้ดี
    *   **ผลกระทบ:** ทำให้ React มองว่า Options เปลี่ยนแปลงตลอดเวลา ส่งผลให้เกิดการวนลูปยิง API ถล่ม Backend (DDoS ตัวเอง) จนโดนบล็อก (Error 429)

## ✅ สิ่งที่ "ควรทำ" (Best Practices & Scalable Patterns)

นี่คือเทคนิคที่เรานำมาใช้แก้ปัญหาและควรยึดเป็นมาตรฐานของโปรเจกต์นี้:

### 1. Universal Grid Pattern (ใช้บล็อกมาตรฐานเดียว)
*   **แนวทาง:** ลบ SwitchCase ทิ้งทั้งหมด และใช้ `<ProductGrid />` คู่กับ `<ProductCard />` เป็นหน้าต่างเดียวในการแสดงผลสินค้า **ทุกหมวดหมู่**
*   **ผลลัพธ์:** หน้าร้าน (Storefront) เป็นอิสระจากข้อมูล Backend จะส่งสินค้าอะไรมา หน้าบ้านก็แค่วนลูป (Map) วาดการ์ดออกมาได้ทันที

### 2. Dynamic Key-Value Builder (สเปคแบบยืดหยุ่น)
*   **แนวทาง:** ในหน้า Add Product (Admin) เปลี่ยนจากฟอร์มตายตัวเป็นระบบ **"เพิ่ม/ลด แถวได้เอง"** (Key-Value Pair)
*   **การเชื่อมต่อ:** แปลงข้อมูลแถวทั้งหมดด้วย `JSON.stringify()` ก่อนส่งเข้า `FormData` ให้ Backend และเวลาลบให้หน้าบ้านส่งค่า `null` เพื่อให้ Backend ใช้ `$unset` ลบออกจาก DB ถาวร
*   **ผลลัพธ์:** รองรับสินค้าได้ทุกประเภทในโลก และไม่กินพื้นที่ Database โดยเปล่าประโยชน์

### 3. Smart Auto-fill & Datalists (ช่วยแอดมินทำงาน)
*   **แนวทาง:** แทนที่จะเว้นว่างให้แอดมินพิมพ์ใหม่ทั้งหมด เราใช้ API ดึง **"โครงสร้างเก่าที่เคยพิมพ์"** (Spec Keys Aggregation) มาวาดช่องรอให้แอดมินเติมค่า (Value)
*   **แนวทาง:** ใช้ `<input list="...">` คู่กับ `<datalist>` สำหรับหมวดหมู่และแบรนด์ เพื่อดึงตัวเลือกจาก Database จริงมาแนะนำ (Auto-suggest) ช่วยลดปัญหาการพิมพ์ผิด (Typo)

### 4. Hook Reference Stability (ป้องกันการวนลูป)
*   **แนวทาง:** ใน Hook ระดับแกนกลางอย่าง `useApi` ต้องใช้ `useRef` ในการกักเก็บค่า `options` และ `apiFunc` เพื่อให้ฟังก์ชัน `execute` มี Reference คงที่เสมอ (`useCallback(..., [])`) ป้องกันการเกิด Infinite Loop

### 5. Preservation vs. Automation (Resilience for New Data)
*   **ปัญหา:** เมื่อทำระบบ Auto-fill (ดึง Template อัตโนมัติเมื่อพิมพ์ชื่อหมวดหมู่) โค้ดที่เขียนไม่ดีมักจะสั่ง "ล้างข้อมูล (set[])" ทันทีที่หา Template ไม่เจอ
*   **บทเรียน:** หากเป็นหมวดหมู่ใหม่ที่ยังไม่มีต้นแบบในระบบ **"ห้ามล้างข้อมูลที่ผู้ใช้กำลังพิมพ์"** เด็ดขาด ระบบต้องฉลาดพอที่จะคงข้อมูลเดิมไว้เพื่อให้แอดมินพิมพ์สเปคใหม่เองได้อย่างอิสระ
*   **เทคนิค:** ใช้ `setTimeout` (Debounce) ในการเช็ค Template เพื่อให้แน่ใจว่าผู้ใช้พิมพ์ชื่อหมวดหมู่จบแล้วจริงๆ ก่อนจะไปดึงข้อมูลมาเปลี่ยนหน้าฟอร์ม

### 6. Database Boundary Sanitization (The Dot (.) Problem)
*   **ปัญหา:** MongoDB และ Mongoose Map **"ห้ามใช้จุด (.) ในชื่อ Key"** (เช่น "Display Size (in.)") ซึ่งจะทำให้เกิด Error 500 ทันที
*   **บทเรียน:** ต้องมี Middleware หรือ Helper ใน Backend เพื่อล้างจุดออกจาก Key ก่อนบันทึก
*   **เทคนิค:** ใช้ **"จุดแบบเต็มตัว (Full-width Dot: ．)"** หรือ Unicode `\uFF0E` แทนที่จุดปกติ ซึ่งในทางสายตา (UI) จะดูแทบไม่ออก แต่ฐานข้อมูลจะยอมรับว่าเป็นตัวอักษรปกติและบันทึกผ่านได้ 100%
